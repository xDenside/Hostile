# Local setup

This is the development setup of the app: an ordinary client and server, on one computer, with
the database inside the server (PGlite, in a folder). It is not yet how Hostile will run for people using it;
see [DESIGN.md](DESIGN.md).
No domain, no accounts with any service, no router changes.

## 1. Prerequisites

| Tool           | Version              | Why                                                   |
| -------------- | -------------------- | ----------------------------------------------------- |
| Node.js        | 24 LTS (>=24.11 <25) | Runtime for the API, the build tools and the scripts. |
| pnpm           | 11.x                 | Workspace package manager.                            |
| livekit-server | 1.13.7               | The media server. Runs natively on your machine.      |

Install LiveKit:

- **macOS** — `brew install livekit` (the official GitHub releases have no macOS build).
- **Windows / Linux** — `pnpm livekit:install` downloads the pinned official release into `.tools/`
  and verifies its checksum.
- Or set `LIVEKIT_BIN` in `.env` to the absolute path of any `livekit-server` you already have.

Check everything at once:

```bash
pnpm check
```

(`pnpm check` runs `scripts/doctor.mjs`. There is no `pnpm doctor` shortcut because pnpm has a
built-in command by that name that would shadow it; `pnpm run doctor` reaches the script too.)

## 2. First run

macOS / Linux:

```bash
pnpm install
pnpm setup:local
pnpm dev
```

Windows PowerShell:

```powershell
pnpm install
pnpm setup:local
pnpm dev
```

The commands are identical on both platforms — every script is plain Node, not bash.

`pnpm setup:local` creates `.env` from `.env.example` (replacing every `__generate__` and `__generate_key__`
value with a random development secret, and keeping values that already exist), checks for livekit-server, and
offers to create development-only test people. `.env` is git-ignored: never commit it. The server creates its
database in `DATA_DIR` (`.local/data` unless `.env` says otherwise) on its first start, and applies new migrations
on every start.

`pnpm dev` starts LiveKit, the API and the web client with prefixed logs and stops them together on
Ctrl+C. The database runs inside the API, and its data stays in `DATA_DIR`.

Open <http://localhost:5190>.

### What `.env` holds

| Variable                                                       | What it is                                                                                                                       |
| -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `HOSTILE_ENV`                                                  | `development` here. A `production` server refuses to start with development values.                                              |
| `WEB_PORT`, `API_PORT`, `LIVEKIT_PORT`, `LIVEKIT_RTC_UDP_PORT` | The ports in section 5.                                                                                                          |
| `API_HOST`                                                     | Where the API listens. Development and test servers refuse anything but loopback.                                                |
| `PUBLIC_APP_URL`                                               | The origin the browser loads the web client from: the Vite dev server.                                                           |
| `LIVEKIT_INTERNAL_URL`                                         | How the API reaches LiveKit, server to server.                                                                                   |
| `LIVEKIT_PUBLIC_URL`                                           | What clients are told to connect to. It must be reachable from every client machine.                                             |
| `LIVEKIT_NODE_IP`                                              | The IP address LiveKit advertises for media. `127.0.0.1` for testing on one machine.                                             |
| `ALLOWED_ORIGINS`                                              | Extra origins allowed to call the API. The desktop origin `hostile://hostile` is always allowed.                                 |
| `DATA_DIR`                                                     | The folder holding the room: the database in `db/`, and attachments in `uploads/`. Empty means `.local/data` in this repository. |
| `UPLOADS_DIR`                                                  | Where files sent in chat are stored. Empty means `uploads/` inside `DATA_DIR`.                                                   |
| `SESSION_SECRET`, `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET`      | Development secrets, generated by `pnpm setup:local`. For development only.                                                      |
| `LIVEKIT_BIN`                                                  | Optional: see section 1.                                                                                                         |
| `COMMUNITY_NAME`                                               | The server's name: what members read at the top of the sidebar.                                                                  |
| `LOG_LEVEL`, `LOG_PRETTY`                                      | How much the server logs, and whether as readable lines (`true`) or as JSON.                                                     |
| `OWNER_SECRET`, `JOIN_AUTO_ADMIT`                              | Development and test only: see section 3.                                                                                        |

## 3. Who you are

For development, `pnpm setup:local` can create two people, Alice (the owner) and Bob, and the seed command
refuses to run unless `HOSTILE_ENV` is `development` or `test`. There is no login. A person is their device, as
"A person is their device" in `docs/DESIGN.md` explains, so a development server needs a way to say who you are:

- **Become the owner.** Set `OWNER_SECRET` in `.env` to at least 32 characters, then in the browser's console on the app's page run
  `fetch('/api/auth/owner', { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify({ secret: 'the value you set', client: 'web' }) })`
  and reload. The hosted app does this by itself with a secret it keeps.
- **Come in as someone new.** Fill in the card and click Ask to join. With `JOIN_AUTO_ADMIT=true` you are let in at once,
  since nobody is at the host's screen.

`OWNER_SECRET` and `JOIN_AUTO_ADMIT` work only on development and test servers, which refuse anything but loopback.
`HOSTILE_ENV=production` refuses both, and refuses to start at all outside the host app: a server of its own has no
room code, so nothing would keep anyone out. The project has no deployment files, so nothing is lost by that.

## 4. Two test users on one machine

**Browser:** open <http://localhost:5190> in a normal window and in a private window (or a second
browser profile). Each window has its own cookie jar, so they are two independent users.

**Desktop:** each profile gets its own Electron user-data directory, identity and single-instance
lock:

```bash
pnpm dev:desktop -- --profile=alice
pnpm dev:desktop -- --profile=bob
```

Run them in two terminals while `pnpm dev` is running in a third; their pages come from its Vite server. Each opens on
the choice: one can host, and the other can join with its code, which uses the public relays.

## 5. Ports

Defaults, all configurable in `.env` (change them if they clash with another project, then rerun
`pnpm check`):

| Port  | Protocol | Variable               | What                           |
| ----- | -------- | ---------------------- | ------------------------------ |
| 5190  | TCP      | `WEB_PORT`             | Web client (Vite dev server)   |
| 4191  | TCP      | `API_PORT`             | API (Express + Socket.IO)      |
| 17890 | TCP      | `LIVEKIT_PORT`         | LiveKit signalling (WebSocket) |
| 17892 | UDP      | `LIVEKIT_RTC_UDP_PORT` | LiveKit media                  |

In the default local profile, LiveKit binds only to the loopback interface and ICE/TCP is disabled,
so nothing is reachable from your network and macOS/Windows will not prompt for firewall access.

## 6. What `pnpm dev` actually starts

- `livekit` — the native binary with a generated config at `.local/livekit.dev.yaml`
  (development-only API key/secret from `.env`, never LiveKit's public `devkey`/`secret`).
- `api` — `apps/server` with file watching, and the database inside it. Only one process can have a
  data folder open, so `pnpm db:seed:dev` refuses while `pnpm dev` is running: stop it first.
- `web` — Vite, proxying `/api` and `/socket.io` to the API so the browser client is same-origin.

## 7. Everyday commands

| Command                            | What it does                                                  |
| ---------------------------------- | ------------------------------------------------------------- |
| `pnpm check`                       | Checks tools, ports, `.env` consistency, database, LiveKit.   |
| `pnpm setup:local`                 | Idempotent setup; safe to re-run.                             |
| `pnpm dev`                         | Runs the stack.                                               |
| `pnpm dev:desktop -- --profile=x`  | Runs the Electron app with its pages from the dev stack.      |
| `pnpm test`                        | Unit + integration tests.                                     |
| `pnpm test:e2e`                    | Playwright, real stack, real media.                           |
| `pnpm build`                       | Builds web, server and desktop bundles.                       |
| `pnpm package:desktop`             | Builds an installable desktop package for the current OS.     |
| `pnpm stack:status`                | Shows which local processes are answering.                    |
| `pnpm test:durability`             | Kills the real server during writes and checks what survived. |
| `pnpm db:reset:DESTROY-LOCAL-DATA` | The only destructive command: erases the local data folder.   |

## 8. Troubleshooting

**"Port is already in use"** — another `pnpm dev` is running, or another project uses the port.
`pnpm check` names the process; change the port in `.env` if needed.

**Voice says the server is unreachable** — `livekit-server` is not installed or not running. Check
the `[livekit]` lines in `pnpm dev`, and `pnpm check`.

**The browser never asks for the microphone** — browsers only grant microphone access in a secure
context. `http://localhost` counts as secure; a LAN IP over plain HTTP does not. See
[TESTING.md](TESTING.md) for LAN setup.

**macOS asks for permissions in the name of your terminal** — when Electron runs unpackaged, macOS
attributes microphone and screen-recording permission to the app that launched it (Terminal, iTerm,
VS Code). A packaged build asks for its own permissions.

**Everything looks stale after switching branches** — `pnpm install`, then restart `pnpm dev` (the
server applies any new migrations when it starts). A database made by a newer branch is refused rather
than guessed at: use another `DATA_DIR`, or `pnpm db:reset:DESTROY-LOCAL-DATA`.

**"The data folder is in use"** — another server or the seed command has it open. A second process would
corrupt it, so the second one refuses. The message names the process and the lock file.

**Writing a migration** — change `prisma/schema.prisma` and add `prisma/migrations/<timestamp>_<name>/migration.sql`
by hand. Prisma's own `migrate` needs a database server to diff against, and this project has none.
A committed migration must not be edited afterwards: the server compares checksums and refuses to start.
